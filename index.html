fast quotas over TCP

Fast counters for limits that matter.

fq is a small specialized database for frequency capping, rate limiting, server-owned and client-owned quota allocation, and high-throughput time-window counters.

Purpose Built

fq avoids general-purpose database scope and focuses on the backend workloads where every request needs a fast counter decision.

Atomic limit decisions

Fixed-window, sliding-window, and token-bucket rate limiters update state atomically per key and window.

Frequency capping

Counter commands cover ad caps, notification limits, signup throttles, and application-owned quota logic.

Quota allocation

Use fixed server-owned quotas, server-decided per-client allocations, or client-owned lease quotas with optional TTL.

Limit-filled streams

Subscribe with STREAM or PSTREAM to receive events when a key/window reaches its configured limit.

Low-latency persistence

Choose memory-only, dump-only, or WAL plus periodic dumps depending on the durability and latency tradeoff.

Async replication

Replicas sync from an initial dump and then apply WAL chunks, with ack tracking and lag metrics on the master.

Operational visibility

Health checks and Prometheus metrics expose TCP connections, WAL behavior, flush latency, and replica progress.

Developer tools

Build the server, CLI client, benchmark client, stress harness, and release report tools from one repository.

Small Protocol

fq uses framed TCP requests with compact text commands, keeping clients simple and responses predictable.

RLIMIT FW

Fixed window

Enforce a maximum number of requests inside each fixed time window.

RLIMIT SW

Sliding window

Limit traffic using the last N seconds instead of a calendar-aligned bucket.

RLIMIT TB

Token bucket

Allow bursts up to capacity and refill tokens over time for smoother throttling.

QUOTA SET / ACQ

Server-owned quotas

Set the quota limit on the server and let clients reserve units without passing policy values.

QUOTA SETN / ACQN

Server-decided quotas

Split a total limit across expected clients and let fq decide how much each acquire receives.

QUOTA ACQL

Lease quotas

Atomically reserve units with a client-supplied limit for explicit client-owned lease workflows.

QUOTA INF

Quota inspect

Read limit, used, remaining, and sorted active client allocations for a quota.

QSTREAM

Quota events

Stream successful quota mutations, or use QPSTREAM to filter events by quota name prefix.

INCR / GET

Counters

Increment, read, delete, watch, and bulk-delete key/window counters.

STREAM

Limit events

Stream frames when rate-limit commands move a key/window from below the limit to filled.

PSTREAM

Prefix streams

Subscribe to the same limit-filled events, filtered to keys that start with a chosen prefix.

Quick Start

Run fq with Docker, download release binaries, or build the server and clients from source.

Run with Docker

docker run --rm \ -p 1945:1945 \ -p 1946:1946 \ -p 2112:2112 \ ghcr.io/fq-db/fq:latest

Mount config.yml and fq_data when you want local persistence configuration and data files.

Build locally

make build make run-server make run-cli

Build outputs include fq, fq-cli, and fq-bench. Release archives provide prebuilt Linux and macOS binaries.

Try a limiter

[fq]> RLIMIT FW user_42 3 60 1;1;2;44 [fq]> RLIMIT FW user_42 3 60 1;2;1;43 [fq]> RLIMIT FW user_42 3 60 1;3;0;42 [fq]> RLIMIT FW user_42 3 60 0;3;0;41

Acquire quota

[fq]> QUOTA SET campaign_42 10 1 [fq]> QUOTA ACQ campaign_42 4 worker_a 60 1;4;4;6;60 [fq]> QUOTA SETN pool_7 10 3 1 [fq]> QUOTA ACQN pool_7 worker_b 1;3;3;7;0 [fq]> QUOTA INF campaign_42 10;4;6;worker_a;4;1788019260 [fq]> QUOTA REL campaign_42 worker_a 1

Watch filled limits

[fq]> STREAM ok|user_42;60;3;42 [fq]> PSTREAM tenant_7_ ok|tenant_7_api;60;100;31

Watch quota changes

[fq]> QSTREAM ok|acq;campaign_42;worker_a;4;4;6;1788019260 [fq]> QPSTREAM campaign_ ok|rel;campaign_42;worker_a;4;0;10;0

Stream behavior

  • Events fire when a limiter fills a key/window for the first time.
  • Rejected rate-limit requests do not emit stream events.
  • Slow subscribers use a bounded per-subscriber event queue.
  • Quota stream events are emitted only for state-changing mutations.

Operational Shape

Persistence modes

  • wal_and_dump for WAL-backed recovery and replication.
  • dump_only for periodic snapshots without per-write WAL.
  • memory for ephemeral high-throughput counter state.

Replication flow

  • Master accepts writes and serves WAL chunks to replicas.
  • Slave restores an initial dump, then continuously applies WAL updates.
  • Lag and replica ack progress are exposed as metrics.
  • Writes are acknowledged by the master without waiting for replica acknowledgement.

Recovery and tuning

  • wal.sync_commit controls whether responses wait for synced WAL batches.
  • engine.partitions reduces per-partition lock contention for hot workloads.
  • engine.wal_apply_workers parallelizes WAL recovery and replica apply work.

Verification tools

  • Benchmark profiles cover smoke, fixed-window, sliding-window, token-bucket, and hot counter workloads.
  • Stress scenarios exercise restart recovery, crash loops, dump recovery, and replication convergence.
  • Release result capture records hardware, runtime, config, profile snapshots, and command manifests.
